# 证据完整性：产物血缘、判决闸门、判据的可执行化

**规则：一个数字看起来正常，不等于它出自你以为的那份代码、那次运行、那套判据。**
[提升声明的审计](measurement-audits.md)管的是“这个增益是不是假的”；本文管的是**更前面一层**——
你手上这份产物，能不能证明它是你想审计的那次运行。两者都过不了时，先说清楚是哪一层出了问题。

本文每一条都来自实际踩坑；括号里是当时的具体症状，可作为识别特征。

## 1. 产物血缘：一份产物可能有两个写入者

**症状（真实案例）**：同一 commit 里，`audit.py` 的类别表有 **6** 个键，而 `results/metrics.json`
记着 `n_classes: 8`，runner 里写的又是 `N_CLASSES`。三者互斥，但**数字本身完全正常**。

**取证顺序**（按成本从低到高，不要跳到结论）：

| # | 证据 | 当时读数 |
| --- | --- | --- |
| 1 | 代码里该类数的唯一真源 | `len(CLASSES)` = 6 |
| 2 | runner 写出该字段的表达式 | `"n_classes": N_CLASSES` → 只能是 6 |
| 3 | 远端执行副本与本地是否逐字节相同 | `diff` 为空 |
| 4 | 运行日志与逐格产物是否逐位一致 | 一致 → 日志确由这套代码产生 |
| 5 | **产物内 `results` 体与 `cells/*.json` 逐位对拍** | **逐位相同** |

结论：`results` 体来自真实运行，**只有 `config` 块出自另一个写入者**（手工合并/旧脚本/复制粘贴）。
一份产物两个来源，就是错误入口。

**影响范围要分开报**：方向性判据（比较、置换、相对 margin）不受类别数影响；
**基线口径受影响**——`1/8 = 0.125` 与 `1/6 = 0.167` 相差 33%，足以让“低于基线”翻成“高于基线”。

**纪律**：

- 每格产物必须自带 `(config, code_sha, seed[, 代码指纹])`，缺一项就等于放弃事后追责。
- 检查器要拿**产物里的 config** 与**代码实际构建的东西**对拍（类别数、目标形状、步数、网格），
  不是只检查 JSON 能否解析。
- `code_sha` 允许是历史提交，判定用“是否为当前 HEAD 的祖先”，不要写成“必须等于 HEAD”
  （文档提交晚于产物是正常情况）。
- 在远端（Space/Job）跑时，容器里是**同步副本**，它的 git HEAD 与源提交无关。
  此时 `code_sha` 要用环境变量显式声明源提交，并另加**代码字节指纹**（对参与运行的文件取哈希）
  才能钉死“跑的是哪几行字节”。

## 2. 判决闸门：缺失会被过滤成通过

**症状（真实案例）**：判决写成

```python
all_pass = all(all(x for x in v.values() if x is not None) for v in verdicts.values())
```

那个 `if x is not None` 把**缺失当成通过**。实测：空网格 → 所有判据 `None` → 全被过滤 → `all(空)` = `True`。

**这类 bug 最危险的地方在于它只在“跑到一半崩了”时发作，而那正是最需要它的时候。**
它不会自曝，因为正常跑完时结果是对的。

**闸门必须是三条并列，缺一不可**：

| 条件 | 含义 | 单独缺失的后果 |
| --- | --- | --- |
| 网格完备 | 每一格、每一个种子都在 | 剩 2 个种子时仍按 80% 规则判“通过” |
| 无未决 | 没有判据返回 `None` | 判据崩了被当成“没意见” |
| 全真 | 已决判据全部为真 | —— |

**配套纪律**：

- 判决函数要独立成模块并**单独测试**，不要散在 runner 的几行 `if` 里。
- 不完备时**只写 `metrics.partial.json` + 非零退出**，绝不写 `metrics.json`。
  文件名本身就是防冒名的最后一道闸。
- 判据只在**观测数等于预期**时给结论；「没过」与「没算」必须在返回值上可区分
  （`False` vs `None`），否则日志里两者长得一样。
- 网格完备性用 `(格名, seed)` 双向对拍，不要用 `zip(learned, frozen)`——
  长度不等时 `zip` 会**静默截断**，把“少了一半”变成“配对良好”。

## 3. 判据自己会怎么错

三条都来自真实踩坑。共同点：**不是结论错，是判据错**。处置一致——保留失败记录，不改判据，另给更强对照。

### 3.1 用错了代理量

**症状**：判据写成「随机目标臂里目标类别可解码 ≤ 0.50」，实测 0.58/0.67 未过。

**根因**：**随机线性映射本就保留输入的类别几何**，所以输出里恒有类别信息。该判据把
“输出含类别信息”误当成“模型用了目标”的代理——它量的是“保几何”，而问题在“保秩”那一层。

**正解**：改用**无需阈值**的对照——同一臂内把目标换成逐样本随机，若 held-out 数字
与对齐目标**逐位相同**，则模型从未使用目标。逐位相同不是 bug，是诊断。

### 3.2 在某些臂上结构上不成立

**症状**：预登记「有意义空间误差 < 冻结随机臂」在三档评价器上各跑一次。CE 档的
**冻结随机臂**拿到 `0.1389`，恰好等于零参数最优常数预测器的分数——因为 CE 头在随机
特征上饱和到均匀分布，而均匀分布正是那个最优常数。

⇒ 该判据在 CE 档比的是**两个都不是坏模型的东西**，它在那里**结构上不成立**，不是“机制失败”。

**处置**：

- 预登记时为每条判据声明**适用档位**（`only_ev: ("ce",)` 之类），预期观测数按适用档缩放；
  这属于预登记的一部分，**必须在开跑前写死**，不能看到结果再决定哪些档算数。
- 发现某条判据在某个臂上不成立时：**原判据保留不改**，另加一条**跨档都成立**的更弱判据
  （例：不是“比随机臂好”，而是“比该档自己的零参数基线好”）。
- 在 SPEC 里写清“这条判据为什么不适用”，而不是悄悄把那一档删掉。

### 3.3 方向写反

**症状**：预登记「有意义空间的有效秩 **>** 冻结随机空间」。实测相反：

| 空间宽度 | 冻结随机 | 有意义空间 |
| --- | --- | --- |
| 96 | 10.6 | **7.1** |
| 252 | 13.6 | **6.9** |
| 384 | 13.9 | **7.0** |

学习在这里的作用是**降秩去噪**，不是增秩。而且有意义空间的秩**与宽度无关**（恒为 ~7），
这个数后来成为一条独立发现。

**处置**：不得事后翻转判据方向。保留失败记录，写明“若重做应改成『两者不同』而非『更高』”，
并把正确方向的量单列为一条诊断。

## 4. 把预登记变成可机器对拍的东西

散文版的预登记只能靠自觉。可执行的版本有三件套：

| 件 | 内容 | 防的是什么 |
| --- | --- | --- |
| **协议锁** `protocol.lock.json` | 网格（维度 × 臂 × 档 × 种子 × 步数）与判据表的 sha256 | 看到结果后偷改网格或判据 |
| **对拍** | runner 开跑前比对锁；不一致**直接拒绝执行** | 静默偏离 |
| **唯一出口** | 显式 `ALLOW_DEVIATION=1`，且偏离写进产物 `protocol_check.diff` | 偏离被隐藏 |

**配对指纹**：多档共用同一初始化时，“配对”原来只有单测保证——单测证明的是**代码逻辑**，
不是**这一次运行的产物**。做法：逐 `(臂, 维度, 种子)` 对共享初始化取哈希，从**产物层**核对三档同值。

**冒烟与结果分离**：冒烟产物必须自带性质声明（`IS_SMOKE_NOT_RESULTS: true`），
检查器据此跳过网格-锁对拍，但**仍然校验判据指纹**——冒烟也要用同一套预登记判据。

## 5. 检查器不能只指向别人（而且守卫自己会静默失效）

**真实的两次自伤**：刚批评完"产物与代码不对应"，下一轮的冒烟产物就出自 `+dirty` 工作树；
再下一轮，守卫改读新格式后**仍按旧字段名取值**，取到 `None`，于是那条检查被**静默跳过**——
而守卫还在报"一致"。

> **"守卫在跑" 不等于 "守卫在查"。** 一个读到 `None` 就跳过的守卫，比没有守卫更危险，
> 因为它提供了虚假的保证。

三条纪律：

- 守卫必须断言**"我读过几条"**：预期 N 条判据，就要打印实际检查了 M 条，`M != N` 直接失败。
- 读到 `None` / 缺字段 / 格式不符 → **报错**，不许当成"不适用"跳过。
- 每次改完代码，把产物**重跑一遍**再入库；脏工作树在 `code_sha` 上标 `+dirty`。

**另一条边界**：检查器要能区分**审计型**（有网格/种子/基线）与**结构测量型**
（只有一个结构量的测量，如秩、谱）产物。用审计型的检查项去套结构测量型，全是假阳性——
我实际踩过：一次给 `v55` 报了 4 个 FAIL，全是误报（它没有分类目标，也没有网格）。
字段位置也要查全：`code_sha` 在顶层、`config` 里、`provenance` 里都见过。

## 6. 一个够用的检查器骨架

八项，按顺序，任何一项 FAIL 都说明“这份产物不能作为结论依据”：

| 项 | 检查 |
| --- | --- |
| F1 | 代码模块可导入（审计型看 `audit.py`，结构测量型看 `measure.py`）|
| L1 | 产物 config 的**类别数/目标形状** == 代码实际构建的 |
| L2 | `code_sha` 是当前 HEAD 的祖先（允许历史提交，不允许外来 sha）|
| L3 | 网格：格数 == 维度 × 臂 × 档；每格行数 == 种子数 |
| L4 | 产物 `results` 体与逐格 `cells/*.json` **逐位对拍** |
| L5 | 配对指纹：同 `(臂, 维度, 种子)` 的各档 `init_sha` 必须相同 |
| L6 | 协议锁 sha 与判据指纹一致，且网格无偏离 |
| V1 | 从逐格数据**重算**关键判决，与产物里存的对拍 |

最后一项最有用：它同时验证了判据代码、数据落盘和聚合逻辑三处。
